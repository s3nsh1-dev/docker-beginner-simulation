MODULE 01

Dev Architecture vs. AWS EC2 Target Architecture

In a beginner setup, your browser talks to localhost:3000 for HTML/JS, and makes independent AJAX requests directly to localhost:5000. On AWS EC2, this breaks completely because "localhost" inside the browser on your phone or laptop refers to your own computer, not the EC2 instance!

❌ Current Beginner Flow

  • Client port 3000 and Server port 5000 are both exposed to host.
  • Client bundle hardcodes http://localhost:5000.
  • Requires permissive CORS (origin: '*').
  • Docker's internal bridge network is essentially bypassed.

✅ Industry Production Flow

  • Only the Client Vite Preview container (port 80/443) is exposed to the internet.
  • Server port 5000 is internal only on the Docker network.
  • Client requests relative path /api/todos; Vite preview's proxy forwards it.
  • No CORS headaches, unified SSL termination, single domain.

MODULE 02

Security: Running as Non-Root User

The Security Risk: By default, Docker containers execute processes as root (UID 0). If an attacker finds a remote code execution vulnerability in an Express dependency, they acquire root privileges inside the container, increasing the risk of container escape onto the EC2 host kernel.

Fix for server/Dockerfile:

The official Node images provide an unprivileged user named node. Transfer ownership of files and set USER node.

# ── Stage 2: Production runtime ─────────────────
FROM node:24-bookworm-slim
WORKDIR /app
ENV NODE_ENV=production

# Install production dependencies
RUN corepack enable && corepack install --global pnpm@12.4.2
COPY package.json pnpm-lock.yaml pnpm-workspace.yaml ./
RUN pnpm install --frozen-lockfile --prod

COPY --from=build /app/dist ./dist
+ # Ensure non-root node user owns application files + RUN chown -R node:node /app + USER node
EXPOSE 5000
CMD ["node", "dist/index.js"]
MODULE 03

Networking: Vite Preview Proxy & Unifying Ports

Right now, your client calls http://localhost:5000/api/todos. To make this container-ready:

  1. Configure preview.proxy in client/vite.config.ts to forward /api to API_TARGET (http://server:5000 in Docker).
  2. Change client's API base to relative path /api/todos.
  3. Stop publishing port 5000 to the public host in Docker Compose.

1. Update client/vite.config.ts:

+ preview: { +  port: 3000, +  strictPort: true, +  host: true, +  allowedHosts: true, +  proxy: { +    '/api': { target: process.env.API_TARGET || 'http://localhost:5000', changeOrigin: true }, +  }, + },

2. Update client/src/services/api.ts:

- const API_BASE = 'http://localhost:5000/api/todos'; + const API_BASE = '/api/todos';

3. Remove public port in docker-compose.yml:

  server:
    build: ./server
    restart: unless-stopped -    ports: -      - "5000:5000" +    expose: +      - "5000" # Available only to other containers in the same network
MODULE 04

Reliability: Healthchecks & Startup Dependency

In your current compose file, depends_on: [server] only guarantees that Docker initiates the container process. It does not wait until Node has initialized or connected to PostgreSQL!

Your server already has a health endpoint at /api/health. Wire it into Docker Compose using the built-in Node 18+ global fetch:

services:
  server:
    build: ./server
    env_file:
      - ./server/.env +    healthcheck: +      test: ["CMD-SHELL", "node -e \"fetch('http://localhost:5000/api/health').then(r => process.exit(r.ok ? 0 : 1)).catch(() => process.exit(1))\""] +      interval: 10s +      timeout: 5s +      retries: 3 +      start_period: 15s

  client:
    build: ./client -    depends_on: [server] +    depends_on: +      server: +        condition: service_healthy
💡 Why Node Fetch? Minimal images like node:*-slim do not have curl or wget installed. Calling node -e "fetch(...)" leverages Node.js without needing extra apk/apt dependencies!
MODULE 05

Build Hygiene: Build Context & .dockerignore

When running docker build, the entire directory is packaged and sent as the Build Context to the Docker daemon.

Found Issue: server/.dockerignore is missing dist/! If you run a local build test on your host machine, host dist/ files get sent to Docker and copied during COPY . ..

Fix server/.dockerignore:

node_modules/ + dist/
.env
.env.*
.git/ + *.log
Why this matters for AWS EC2:

Smaller build contexts mean faster Git pulls, faster CI/CD pipelines, and zero risk of stale local JavaScript overwriting container TypeScript outputs.

MODULE 06

Container Lifecycle: PID 1 & Graceful Shutdown

In Linux, the process with Process ID 1 (PID 1) has special responsibilities: reaping zombie processes and handling system signals like SIGTERM and SIGINT.

Node.js was not designed to run as PID 1. By default, it ignores SIGTERM. When you run docker stop or restart services on EC2, Docker waits 10 seconds, times out, and forcefully kills Node with SIGKILL, risking in-flight database transaction corruption!

Solution: Use Docker's built-in init system (Tini)

services:
  server:
    build: ./server +    init: true # Uses tini as PID 1 to reap zombies and forward signals

Handle SIGTERM in server/src/index.ts:

+ const server = app.listen(PORT, () => ...);
+ process.on('SIGTERM', async () => { +  console.log('SIGTERM received. Shutting down gracefully...'); +  server.close(async () => { +    await pool.end(); +    process.exit(0); +  }); + });
MODULE 07

AWS EC2 Production Deployment Checklist

When taking this containerized stack onto an AWS EC2 instance (e.g. t3.micro or t4g.small), adhere to these battle-tested standards:

1. EC2 Security Group (Firewall) Rules

Only allow inbound traffic on:
• Port 22 (SSH): Restricted to your IP address only.
• Port 80 (HTTP) & 443 (HTTPS): Open to 0.0.0.0/0.
• NEVER expose Port 5000: The Express API should only be reached via internal container network.

2. Docker Log Rotation (Prevent Disk Fill)

On EC2, containers that run for months will fill up your EBS volume with logs if unconfigured. Add log rotation to docker-compose.yml:

logging:
  driver: "json-file"
  options:
    max-size: "10m"
    max-file: "3"
3. Secrets & Environment Variables on EC2

Never commit .env to GitHub. On EC2:
• Create /home/ubuntu/app/server/.env directly on the server, or pull it using AWS Systems Manager (SSM) Parameter Store.
• Set permissions: chmod 600 server/.env so only your user can read database credentials.

4. SSL / HTTPS Setup

Attach an Elastic IP to your EC2 instance and point your domain (via Route53/Cloudflare). Place an AWS Application Load Balancer (ALB) with AWS Certificate Manager (ACM) or Cloudflare SSL in front of your EC2 instance.
